## 1. Lighting and global illumination

### 1.1 Radiance cascades — **not viable here**

Sannikov-style radiance cascades are the loudest 2025–26 GI research line, and there are now
real WebGPU implementations: a WGSL compute-shader infinite-bounce solver
([nff747/radiance-cascades-wgsl](https://github.com/nff747/radiance-cascades-wgsl), accessed
2026-09-25) and a three.js 3D variant built on screen-space probes + `three-mesh-bvh`
([CodyJasonBennett/three-rc](https://github.com/CodyJasonBennett/three-rc), accessed
2026-09-25). Split Radiance Cascades via sparse radiance probes is a 2026 paper
([arXiv 2607.20384](https://arxiv.org/pdf/2607.20384), 2026).

**Verdict: no.** Every usable path needs WebGPU compute, i.e. it excludes ~30 % of mobile
(§6) and forfeits the entire pmndrs post stack. More importantly it solves a problem this app
does not have — the diffuse GI here is *already* a Cycles path-trace, which is strictly better
than any real-time approximation. Radiance cascades would buy dynamic GI (re-lighting as the
sun moves) at enormous cost; the weather/sun system already fakes that convincingly by
re-baking and re-fitting gains.

### 1.2 Screen-space GI — **no, and the author agrees**

`0beqz/realism-effects` (SSGI, TRAA, motion blur) is the only SSGI option for WebGL three.js
([github.com/0beqz/realism-effects](https://github.com/0beqz/realism-effects), accessed
2026-09-25). Its v2 / `poisson-recursive` rewrites have sat unreleased on branches. The
predecessor `screen-space-reflections` package is explicitly deprecated in favour of it
([npm](https://www.npmjs.com/package/screen-space-reflections), accessed 2026-09-25).

The more useful data point is the practitioner verdict in the three.js forum SSGI thread
(first post 2025-07-15, updated 2026-01-23):
> "It's mostly hype at this point. AO is small-scale and inaccurate and tracing rays is expensive."
— and the technique is accurate only within ~1 m radius; beyond that it invents off-screen data
([discourse.threejs.org/t/85190](https://discourse.threejs.org/t/ssgi-screen-space-global-illumination/85190)).

**Verdict: no.** A 1 m-radius indirect term on top of a full Cycles irradiance bake is double
counting, which is precisely the mistake `(z)5` already made and deleted.

### 1.3 Light probes / irradiance volumes / SH grids — **partially relevant**

three.js has `LightProbe` (9-coefficient SH, diffuse only), shipped since
[PR #16223](https://github.com/mrdoob/three.js/pull/16223) (2019), documented at
[threejs.org/docs LightProbe](https://threejs.org/docs/pages/LightProbe.html) (accessed
2026-09-25). A **volume** of them — the thing that would light *dynamic* furniture correctly —
has never landed: donmccurdy's `LightProbeVolume` PR
([#18371](https://github.com/mrdoob/three.js/pull/18371), 2020) is still unmerged, and the
community substitute is a Blender-bake-to-cubemap plugin
([discourse.threejs.org/t/57921](https://discourse.threejs.org/t/probes-volume-purposal-for-three-js/57921),
accessed 2026-09-25) plus [gillesboisson/threejs-probes-test](https://github.com/gillesboisson/threejs-probes-test).
`WishGI` (arXiv 2506.01288, 2026) reports most objects need <30 SH probes for high-precision
representation, 256 for the worst case.

**Relevance here is narrow but real.** Static shell surfaces already have per-texel baked
irradiance, so a diffuse probe volume adds nothing to them. The gap is (a) *furniture the user
moves*, which currently receives only the single global procedural probe + analytic lights, and
(b) **specular**, which SH probes cannot represent at all. (b) is the bigger tell — see §2.2.

### 1.4 What a shipping competitor actually does

Shapespark — a commercial browser archviz product on the same technical footing (baked
lightmaps + WebGL) — spent 2026 on *bake quality and mobile*, not on real-time GI: a light-tree
sampler to cut noise, lower default sample counts, **WebGL2 on iOS**, and **centroid sampling
to kill lightmap aliasing on iOS**
([shapespark.com/changelog](https://www.shapespark.com/changelog), accessed 2026-09-25).
That is a direct endorsement of the architecture already chosen here, and the centroid-sampling
detail is a concrete, cheap idea worth stealing if lightmap edges ever shimmer on iOS.

### 1.5 Free wins from a three.js upgrade (r184 → r186+)

This repo pins `three ^0.184.0`. Landed since:

- **r185: clustered (Forward+) lighting** — `WebGPURenderer` only, but the direction of travel.
- **r186: `SunLight` addon with cascaded shadow maps, for *both* renderers**.
- **r186: PBR reworked for energy conservation** on diffuse and sheen.
- **r186: `SSAONode` with depth-aware blur; `OITPassNode` for order-independent transparency.**
- **r183: `PostProcessing` renamed `RenderPipeline`** (old name warns).
- **Deprecated:** `PCFSoftShadowMap` folded into `PCFShadowMap`; `Clock` → `Timer`; minified
  builds removed in r186; custom `Object3D` subclasses must call `super.dispose()`.

Sources: [utsubo, "What's New in Three.js (2026)", 2026-09-24](https://www.utsubo.com/blog/threejs-2026-what-changed);
[three.js r186 release notes](https://github.com/mrdoob/three.js/releases/tag/r186) (accessed 2026-09-25).

The **energy-conservation rework** matters for this app specifically: sheen is used on every
upholstery and drapery preset (`src/materials/materialRealism.ts`), and CSM `SunLight` is
directly relevant to the plan-fitted shadow frustum in `src/scene/lighting/shadowFrustum.ts`.
A version bump is cheap and is the only item here that needs no new code. Caveat: it will
require re-validating the AgX/Cycles gain fit, because a PBR energy change moves measured luma.

## 2. Reflections

### 2.1 SSR — **no**

- `postprocessing` (pmndrs) **no longer exports SSR at all**; the standalone
  `screen-space-reflections` package is deprecated
  ([npm](https://www.npmjs.com/package/screen-space-reflections), accessed 2026-09-25).
- three.js' own `webgl_postprocessing_ssr` example is the legacy `SSRPass` and looks it.
- The maintained SSR is the **WebGPU `ssr()` TSL node**
  ([threejs.org webgpu_postprocessing_ssr example](https://threejs.org/examples/webgpu_postprocessing_ssr.html),
  accessed 2026-09-25).
- SSR is structurally wrong for interiors anyway: it has no data for anything off-screen or
  behind an occluder, which in a 1.9 m HDB kitchen is most of the reflected hemisphere.

**Verdict: no** on any tier, on any backend, for this app.

### 2.2 Parallax-corrected (box-projected) cubemap probes — **the standout opportunity**

Lagarde's box-projected local IBL (SIGGRAPH 2012) has an official three.js example
([PR #15897](https://github.com/mrdoob/three.js/pull/15897), 2019; live mirror
[webgl_materials_envmaps_parallax](https://mjurczyk.github.io/three.js/examples/webgl_materials_envmaps_parallax.html),
accessed 2026-09-25). It corrects the reflection vector against a room-sized AABB so a cubemap
sampled from one point stays correct as the camera walks the room. It is explicitly described
in the community as the technique for "believable fake reflections for room-size environments"
([discourse.threejs.org/t/32692](https://discourse.threejs.org/t/parallax-correction-from-environment-maps/32692),
accessed 2026-09-25). The known wart is that the upstream example has broken and been re-fixed
several times against shader-chunk churn
([issue #18111](https://github.com/mrdoob/three.js/issues/18111), 2019) — i.e. it is a shader
injection that must be pinned to a three version.

**Why this is the highest-value visual item here.** The diffuse half of the light transport is
a Cycles bake; the specular half is one 64–256 px procedural Lightformer probe shared by the
whole flat. Every glossy surface in a Singapore HDB — floor tiles, glazed bathroom and kitchen
wall tiles, the mirror surround, chrome fittings, the glass hob, appliance fronts — is
currently reflecting a generic studio, not *this room*. That mismatch is the classic
"lightmapped-but-still-CG" tell, and it is the one gap the whole lightmap arc has not touched.
Blender/Cycles cubemap bakes are already a solved workflow in this repo (`docs/skills/blender.md`).

### 2.3 Planar reflectors — **already shipped; do not extend**

`MeshReflectorMaterial` is in at 512/1024 px on `realistic`. Extending planar reflection to
floors would re-render the scene per reflective plane; the community consensus on
`CubeCamera`/planar reflection cost is unambiguous ("uses too much performance and can run very
laggy", [discourse.threejs.org/t/47098](https://discourse.threejs.org/t/cubecamera-reflection-issue-codepen-included/47098),
accessed 2026-09-25). A **static, offline-baked** cubemap (§2.2) costs zero per-frame draws and
is the right trade for a flat whose shell never moves.

## 3. Materials

### 3.1 KHR extension coverage in three r184+

`MeshPhysicalMaterial` supports clearcoat, sheen, iridescence, transmission, thickness, IOR,
anisotropy and specular
([threejs.org/docs MeshPhysicalMaterial](https://threejs.org/docs/pages/MeshPhysicalMaterial.html),
accessed 2026-09-25); anisotropy landed via [PR #25580](https://github.com/mrdoob/three.js/pull/25580).
r186 additionally adds **retroreflectivity** with environment lighting
([r186 notes](https://github.com/mrdoob/three.js/releases/tag/r186)).

Against this repo's inventory: **transmission, clearcoat, sheen and anisotropy are already in
use.** The unused ones are:

- **Iridescence** — soap-bubble/thin-film. No interior surface in an HDB flat wants this.
  *Skip.*
- **Dispersion** — chromatic separation through thick clear volumes. Visible on a crystal
  tumbler, invisible on a window pane. *Skip.*
- **`KHR_materials_specular`** — lets you dial dielectric F0 below the hardcoded 0.04. Genuinely
  useful for matte emulsion paint and unglazed floor tile, which are *less* reflective than the
  default. Cheap (one float, no extra pass). *Small but real.*
- **Volume / attenuation colour** — a green edge on thick glass. Only visible on shower screens
  viewed edge-on. *Marginal.*

The documented caveat stands: `MeshPhysicalMaterial` "has a higher performance cost per pixel
than other three.js materials, with most effects disabled by default and adding cost as they
are enabled" (same docs page) — which is why the tier gate in
`src/materials/materialRealism.ts:transmissionTiers` is correct and should not be loosened.

### 3.2 Parallax-occlusion mapping for tile grout and plaster — **strong #4**

POM "procedurally creates 3D definition in textured surfaces using a displacement map instead
of generating new geometry", and gives near-relief-mapping quality more cheaply
([Wikipedia: Parallax occlusion mapping](https://en.wikipedia.org/wiki/Parallax_occlusion_mapping),
accessed 2026-09-25; [LearnOpenGL: Parallax Mapping](https://learnopengl.com/Advanced-Lighting/Parallax-Mapping),
accessed 2026-09-25). The canonical archviz-context three.js implementation is published by
**Shapespark** — a shipping browser archviz product —
([github.com/shapespark/parallax-mapping](https://github.com/shapespark/parallax-mapping),
accessed 2026-09-25), which is about as strong a production endorsement as exists for this
class of app. Adobe's framing is exactly our use case: recessed grout lines in a flat texture
([Substance 3D: what is parallax mapping](https://www.adobe.com/ie/products/substance3d/discover/what-is-parallax-mapping.html),
accessed 2026-09-25).

An HDB flat is tiled from the kitchen splashback to both bathrooms to the service yard. Grout
that has actual depth at grazing angles — which is *most* of what a walking camera sees — is a
tactile realism win that no lighting change can substitute for. Implementation is an
`onBeforeCompile` patch on the existing tiling materials, tier-gated, with an iteration-count
knob. Risk: it is a shader injection (same fragility class as §2.2) and it breaks down at
extreme grazing angles and silhouettes.

### 3.3 Curtains and sheers

Nothing new to import: `sheen` + `transmission` is already the documented three.js recipe for
sheer fabric, and this repo already has both plus `src/materials/draperyOpacity.ts` with a
daylight transmission floor. The only calibration datum worth recording is that real sheer
voile/chiffon transmits **80–95 %** of incident light (industry figure, surfaced 2026-09-25) —
worth sanity-checking `draperyOpacity.ts` against. The r186 **sheen energy-conservation
rework** (§1.5) is the relevant upstream change.

## 4. Camera and presentation

The archviz-photography canon is remarkably stable, and it contradicts a couple of common
real-time defaults:

- **Focal length.** Avoid anything shorter than 30 mm; work in **35–55 mm**, with 50 mm "the
  best resemblance to what we humans see". Wide angles are "criminally overused in arch-viz"
  because of the pressure to show the whole room in one frame
  ([Ronen Bekerman, "Photographic Approach in Architectural Visualisation", 2013-03-26](https://www.ronenbekerman.com/photographic-approach-in-architectural-visualisation/)).
  This is the single most-cited rule and it survives into 2026 guidance
  ([D5 Render, "Camera Setting Tips Must Known for Archviz"](https://www.d5render.com/posts/camera-setting-tips-must-known-for-archviz),
  accessed 2026-09-25).
- **Exposure.** "The world is a very grey place" — only the brightest spot should approach pure
  white; other whites should land **190–220** of 255 (Bekerman, 2013). Worth holding against
  `(l)` WINDOW-LUMINANCE, which is still open with the app clipping 0.33 % of glazing versus
  15–39 % in the reference photographs.
- **Two-point perspective.** Keep verticals vertical; corner (2-point) framing reads best for
  interiors (Bekerman, 2013). Converging verticals are an instant "this is a game camera" tell.
- **Depth of field.** Useful "for scale cues and image focus… it should support the composition
  rather than draw attention to itself"; for a clean archviz render the default is a *high*
  f-stop so DoF never blurs anything (D5, accessed 2026-09-25). This repo's default
  `dofFStop = 0` (off) is correct; `rasterDofParams` should stay conservative.
- **Grain / bloom / vignette / CA.** "Subtle camera imperfections such as bloom, slight
  vignette, restrained chromatic aberration, or light film grain can be introduced in a
  controlled way… less is usually more"
  ([Kunkun Visual, "Architectural Visualization Trends 2026"](https://www.kunkunvisual.com/post/architectural-visualization-trends-2026-what-s-actually-changing-in-archviz-and-what-it-means-for),
  accessed 2026-09-25). This repo's calls — grain 0.035–0.07, vignette 0.55, CA behind a
  default-off flag — are squarely inside the 2026 consensus. **No change recommended.**
- **Head-bob.** Consensus is against it for comfort: artificial camera shake and head bobbing
  should be avoided to reduce motion sickness, and most games that keep it ship **30–60 % of
  "realistic" amplitude** plus an accessibility toggle; "no bob is always safer, but zero bob
  can feel floaty"
  ([GameDev.net, "Bodycam-style realistic head-bobbing…"](https://gamedev.net/forums/topic/719653-bodycam-style-realistic-head-bobbing-motion-for-first-person-controllers/5473086/),
  accessed 2026-09-25; corroborated by the VR-comfort literature, e.g.
  [arXiv 2006.15432](https://arxiv.org/pdf/2006.15432), 2020).
  **Verdict: skip head-bob.** For a *showroom* — where the user is evaluating a home, not
  playing a game — nausea risk buys nothing. Damped camera motion (already present) is the
  version of this idea that is worth having.

**Net: the camera/presentation layer is the one area where this app is already at or above
the 2026 bar.** The only open item worth acting on is the 35–55 mm default check in
`src/scene/cameras/cameraLensSettings.ts`.

## 5. Post-processing and anti-aliasing

### 5.1 The MSAA-vs-AO problem, and how the field actually solves it

This is the repo's `z22` / MSAA-DEPTH-BLIT, and it is a known, named, general problem — not a
local mistake:

- pmndrs' own docs: the `multisampling` option "may produce visual artifacts when used with
  some effects such as SSAO and should not be regarded as a blanket antialiasing solution"
  ([postprocessing v6.13.0 release notes](https://github.com/pmndrs/postprocessing/releases/tag/v6.13.0),
  accessed 2026-09-25).
- N8AO carries the exact error this repo hit:
  *"WebGL2: glBlitFramebuffer: Read and write depth stencil attachments cannot be the same image"*
  ([N8python/n8ao issue #53](https://github.com/N8python/n8ao/issues/53), accessed 2026-09-25).
- There is a *documented workaround* that is not "turn MSAA off": detect that the provided
  depth texture is the same as the one bound to the output buffer, allocate an extra
  framebuffer, run a `CopyPass` into it, and bind the copy as the AO input
  ([Casey Primozic, "Fixing pmndrs Postprocessing Recursive Depth Texture Binding"](https://cprimozic.net/notes/posts/fixing-pmndrs-postprocessing-recursive-depth-texture-binding/),
  accessed 2026-09-25).
- iOS specifically has its own multisample depth/stencil bug on top of this
  ([pmndrs/postprocessing issue #412, "Multisampling on newer iOS depth/stencil issue"](https://github.com/pmndrs/postprocessing/issues/412),
  accessed 2026-09-25) — relevant to the unresolved iOS-only `z21` BATHROOM-BLACK-BLOB.
- Needle's write-up states the underlying reason cleanly: averaging depth across an edge yields
  "a depth that's neither near nor far", so depth-consuming effects break; their prescription is
  to do AA as the **final post pass** instead — while conceding that "geometry-heavy projects
  like realtime automotive or architectural rendering can still benefit" from real MSAA
  ([Needle, "Antialiasing and Post-Processing"](https://cloud.needle.tools/articles/antialiasing-and-postprocessing),
  undated, accessed 2026-09-25).
- pmndrs' general recommendation: MSAA as default, SMAA "for weaker devices or when MSAA
  produces artifacts", and with N8AO specifically "hardware antialiasing does NOT work with
  ambient occlusion… use of SMAAPass is recommended"
  ([pmndrs/postprocessing Antialiasing wiki](https://github.com/pmndrs/postprocessing/wiki/Antialiasing),
  accessed 2026-09-25).

**So the field's answer is exactly the fix already named in `z22`: give AO its own
non-multisampled depth source.** The `CopyPass` pattern above is the concrete recipe. That
unblocks MSAA on every tier *and* keeps SMAA for the shader aliasing MSAA cannot touch — which
is precisely the combination `EffectsImpl.tsx` already reasons about in its `multisampling`
comment.

### 5.2 TAA — **not available on the WebGL path**

pmndrs has an open `TAAEffect` issue, blocked on `GBuffer.VELOCITY`
([issue #574](https://github.com/pmndrs/postprocessing/issues/574), accessed 2026-09-25) and a
long-open predecessor ([issue #238](https://github.com/pmndrs/postprocessing/issues/238)).
The only shipping TAA for three.js is either `realism-effects`' TRAA (unmaintained release, §1.2)
or the **WebGPU `traa()` TSL node**. three's own `TAARenderPass` accumulates jittered samples
and "creates high quality anti-aliased results **when there is no motion**"
([threejs.org webgl_postprocessing_taa example](https://threejs.org/examples/webgl_postprocessing_taa.html),
accessed 2026-09-25) — i.e. it is a stills tool, not a walkthrough tool.

**Verdict: no TAA on the current backend.** MSAA-with-a-proper-depth-prepass + SMAA is the
correct 2026 WebGL answer and is within reach.

### 5.3 Upscaling instead of DPR degradation — **watch, don't build**

r184 added **FSR 1 and TAAU upscaling nodes**; `@pmndrs/upscaler` is a WGSL FSR2/3 temporal
upscaler with reactive masks, auto-exposure and composable TSL nodes, described as
"feature-complete and GPU-verified", requiring three r184+ and **WebGPU with no WebGL fallback**
([github.com/pmndrs/upscaler](https://github.com/pmndrs/upscaler), accessed 2026-09-25;
[utsubo 2026-09-24](https://www.utsubo.com/blog/threejs-2026-what-changed)).

This is the principled alternative to open item `(z)7` — "`dprMax` 2 → 1 as the last demotion
rung, decided YES, not started", flagged there as the largest unused perf lever (4.5×). Render
at 1.0 and *reconstruct* to 2.0 rather than simply going soft. But it is WebGPU-only, so it is
gated behind §6. **Record it as the reason `(z)7` should ship as a plain DPR rung now and be
revisited if/when a WebGPU path exists.**

## 6. Rendering backend: is WebGPU viable in 2026?

**Support is there. The migration cost is not worth it for this app this year.**

Support:
- Safari 26 shipped WebGPU across macOS/iPadOS/iOS/visionOS in September 2025
  ([App Developer Magazine, "WebGPU in iOS 26"](https://appdevelopermagazine.com/webgpu-in-ios-26/),
  accessed 2026-09-25).
- W3C posted WebGPU as a **Candidate Recommendation Draft dated 2026-05-12**
  ([webgpu.com news](https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/),
  accessed 2026-09-25).
- Coverage figures disagree and both matter: ~87 % global as of August 2026
  ([utsubo migration guide, 2026-09-24](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)),
  but only **~70 % of *mobile* devices in active use**
  ([webo360, "WebGPU Browser Support in 2026"](https://webo360solutions.com/blog/webgpu-browser-support/),
  accessed 2026-09-25). **Firefox on Linux and Android still lack it in stable.**

Cost, from the migration checklist ([utsubo, 2026-09-24](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)):
- **`EffectComposer` and pmndrs/postprocessing are incompatible with `WebGPURenderer`** — you
  must move to `RenderPipeline` + TSL nodes. That is `src/scene/EffectsImpl.tsx` rewritten from
  scratch, including the AgX/Cycles parity work and every measured constant in
  `src/scene/look.ts`.
- **`ShaderMaterial`, `RawShaderMaterial` and `onBeforeCompile` do not work** — *not even on the
  WebGL2 fallback backend*. That kills `src/scene/applyVisibilityLightmaps.ts` (the lightmap
  `replace`-mode injection), the mitre/GI shader patches, and any POM or box-projection patch
  (§2.2, §3.2) until all are ported to TSL.
- drei `Text` (uses `onBeforeCompile`) and drei `Environment` with child renderers (creates
  `WebGLCubeRenderTarget`, removed r183) both break. This repo uses `<Environment>` in
  `src/scene/lighting/SceneEnvironment.tsx`.
- `renderer.getContext()` / `renderer.capabilities` break — used by
  `src/scene/AnisotropyController.tsx`, `src/materials/convert/decodeGpuTexture.ts` and the
  software-rasteriser detection in `src/scene/quality.ts`.
- Async init: `render()` on an uninitialised renderer **throws** in r186.
- **Performance is not a guaranteed win**: "developers report scenes where `WebGPURenderer` is
  slower than `WebGLRenderer`". The gains concentrate in high-draw-call and compute-heavy
  scenes — this app is a small mesh count with an expensive fragment stage.

**Verdict: do not migrate in round 7 or 8.** The realistic posture is: keep WebGL2; upgrade
three to r186+ for the WebGL-side wins (§1.5); write any *new* shader work in a way that could
be ported (single injection point, documented); revisit when `RenderPipeline`'s `ssr`/`ssgi`/
`traa` nodes plus the FSR upscaler together justify the rewrite, and when mobile coverage is
past ~90 %.

## 7. Asset pipeline

### 7.1 KTX2 is the biggest untouched lever, and it is a *mobile survival* issue

Findings:
- KTX2 + Basis "stays compressed all the way into VRAM by transcoding to a GPU-native format
  (BC on desktop, ASTC or ETC2 on mobile), which typically cuts texture memory **4× to 8×**"
  (surfaced 2026-09-25; the canonical primer is
  [donmccurdy, "Choosing texture formats for WebGL and WebGPU applications", 2024-02-11](https://www.donmccurdy.com/2024/02/11/web-texture-formats/)).
- That article's hard number: a **4096² image with mipmaps is 90 MB uncompressed in GPU
  memory**, and "decompression and upload prevent WebGL from doing other work, a very common
  source of dropped [frames]".
- ETC1S vs UASTC: ETC1S is the default, JPEG-class size, weak on data textures like normal maps;
  UASTC matches BC7, suits normal maps and hero assets, and is only 1–2× JPEG after Zstd
  supercompression (donmccurdy, 2024-02-11).
- **Safari/iOS never exposes S3TC** and wants ETC2 or ASTC — which is exactly the case KTX2's
  load-time transcode exists to handle (surfaced 2026-09-25).
- **iOS Safari enforces roughly a 300–500 MB WebGL heap**, far below desktop; guidance is ASTC
  plus capping web textures at 1024² absent a specific reason
  ([Wonderland Engine, "WebGL Performance on Safari and Apple Vision Pro"](https://wonderlandengine.com/news/webgl-performance-safari-apple-vision-pro/),
  accessed 2026-09-25). Memory is the single most common cause of iOS WebGL crashes
  ([bugnet.io, "Fix: Unity WebGL Build Crashing on Safari iOS"](https://bugnet.io/blog/how-to-fix-unity-webgl-build-crashing-on-safari-ios),
  accessed 2026-09-25).
- Khronos' own framing: KTX2 exists to make glTF assets compact *and* GPU-resident
  ([Khronos press release](https://www.khronos.org/news/press/khronos-ktx-2-0-textures-enable-compact-visually-rich-gltf-3d-assets),
  accessed 2026-09-25).

Against this repo: **230 lightmap PNGs are loaded through a bare `TextureLoader`**
(`src/scene/VisibilityLightmaps.tsx:234`) and therefore live in VRAM as uncompressed RGBA.
Separately, drei's `useGLTF` **does not wire a `KTX2Loader` into the `GLTFLoader` at all** —
`src/furniture/gltf/decoders.ts` documents this explicitly — so no shipped GLB can carry
`KHR_texture_basisu` today, and the offline `optimize:glb` `--ktx2` path silently falls back to
WebP when `toktx` is absent. Net: **zero shipped `.ktx2` assets** outside test fixtures.

This is very likely a contributing factor to the unresolved iOS-only defects (`z21`
BATHROOM-BLACK-BLOB) and it is the reason the higher-resolution lightmap re-bake was rejected
on cost (N8-RES) — with 4–8× compression, that rejection may no longer hold.

### 7.2 Progressive / streamed loading — worth knowing, not urgent

Needle's `gltf-progressive` is the mature pattern: a tiny initial file with embedded low-quality
proxies plus higher-quality LOD files streamed on demand, LODs chosen by **mesh screen density
rather than raw distance**, and per-texture progressive loading (low-res first, full quality on
demand)
([Needle Engine docs: gltf-progressive](https://engine.needle.tools/docs/gltf-progressive/),
accessed 2026-09-25; available standalone for vanilla three/R3F/model-viewer via
[npm](https://www.npmjs.com/package/@needle-tools/gltf-progressive)). Their optimisation guide
also confirms the Draco/Meshopt split this repo already follows — Meshopt where morph targets or
animation must survive, Draco otherwise
([Needle optimisation guide](https://engine.needle.tools/docs/how-to-guides/optimization/),
accessed 2026-09-25).

This repo already has discrete `-low`/`-medium`/original LOD tiers keyed off the render tier,
which captures most of the benefit. The remaining gap is the **1459 ms load hitch (`(z)6`)** and
the 216 ms lightmap-attach compile frame — both are compile/upload stalls, which is a §7.1
problem (upload cost) more than a streaming problem.

### 7.3 Gaussian splatting — **not applicable**

2026 is widely called the inflection year for 3DGS in archviz and real-estate tours
([utsubo, "3D Gaussian Splatting: Complete Guide… (2026)"](https://www.utsubo.com/blog/gaussian-splatting-guide),
accessed 2026-09-25), with web-deliverable showcases like the Grace Cathedral tour (2026-07-20).
**It is irrelevant here:** 3DGS reconstructs a place that physically exists from photographs.
This app's whole value is a *configurable* flat — move the sofa, change the finish, change the
hour. Splats are not editable, not relightable, and not finish-swappable. Note it and move on.

## 9. The three highest-value next moves, wired into this codebase

### #1 — Parallax-corrected per-room specular cubemap probes

**Why.** Diffuse light transport is a Cycles bake; specular is one shared 64–256 px procedural
Lightformer. Every glossy surface in the flat reflects a generic studio instead of its own room.
Fixing that is the last untouched half of the light transport, and the Blender bake workflow
already exists.

**Shape.** Offline-bake one small cubemap per room from the room centroid in Cycles (same rig as
the lightmap bake), ship as KTX2 (depends on #3), and box-project it per-room at runtime. Static
— zero per-frame draw calls, unlike `CubeCamera` or planar reflection.

**Files.**
- **New** `src/scene/lighting/roomProbes.ts` — pure module: room-id → `{ cubemapUrl, boxMin,
  boxMax, probeCenter }`, derived from the plan the way `src/scene/lighting/daylitRooms.ts` and
  `src/scene/lighting/planAttenuationWalls.ts` already derive per-room data. Unit-testable with
  no renderer, matching the existing `*.test.ts` convention in that folder.
- **New** `src/scene/lighting/boxProjectEnv.ts` — the `onBeforeCompile` chunk that replaces the
  `envmap_physical_pars_fragment` reflect-vector with the AABB-corrected one (three's
  `webgl_materials_envmaps_parallax` example is the reference). Pin the three version in a
  comment — this chunk has broken upstream twice
  ([three.js #18111](https://github.com/mrdoob/three.js/issues/18111)).
- **New** `src/scene/lighting/RoomProbes.tsx` — R3F component that assigns `material.envMap` +
  the box uniforms per mesh, mirroring how `src/scene/VisibilityLightmaps.tsx` walks the shell
  and attaches `lightMap`/`uv1`. Reuse its mount-once discipline (a mid-session attach already
  costs a measured 216 ms compile frame — same hazard applies here, so attach at the same
  moment).
- **Edit** `src/scene/lighting/SceneEnvironment.tsx` — keep the global probe as the fallback
  for meshes with no room assignment and for the orbit dollhouse; do not remove it. Respect
  `iblSignal.ts`/`setIblActive` so the metalness clamp still applies.
- **Edit** `src/scene/quality.ts` — add `roomProbeResolution` to `QualitySettings`
  (`0 / 0 / 64 / 128`), so `perf·*` keeps the single global probe.
- **New flag** in `src/features/featureFlags.ts` — `roomProbes`, `tier: 'pro'`? No: this is
  invisible plumbing that improves the default look, so `tier: 'simple'`, `default: true` once
  measured. Unit-test both Simple and Pro per CLAUDE.md.
- **New** bake script alongside the existing Blender lightmap tooling; extend
  `src/scene/lightmapIndex.ts`'s manifest convention rather than inventing a second one.
- **Guard** `src/scene/postStackGuard.test.ts` has no bearing; add
  `src/scene/lighting/roomProbes.test.ts` + a box-projection maths test.

**Watch for.** Probe/lightmap double counting — the bake already contains the diffuse bounce, so
the probe must contribute **specular only** (`envMapIntensity` on a material whose diffuse comes
from `lightMap` in `replace` mode). Getting that wrong repeats the `(z)5` error. Measure in
linear (`isLinearView()`), per the AGX-PARITY lesson: app counts ≠ Cycles counts.

### #2 — Give N8AO its own depth pre-pass, then turn MSAA back on everywhere

**Why.** `z22` MOBILE-BLACK-FLICKER is currently *mitigated, not fixed*: `mobileMsaaSamples()`
forces `msaa = 0` whenever `ao` is on, and since `ao` is true on every tier that runs the full
stack, **the `mobileMsaa` flag can never fire**. The cost is aliased geometry edges on exactly
the tiers meant to look best, on exactly the devices (phones at DPR 1–1.5 after interactive
degrade) where aliasing is most visible. The field's fix is published (§5.1) and the repo's own
`z22` note already names it.

**Shape.** Break the aliasing between the composer's multisampled depth attachment and N8AO's
depth input: allocate a separate non-multisampled depth target and `CopyPass` into it, then bind
that as AO's depth source — the pattern documented by Primozic. With that in place, MSAA and
N8AO coexist, and SMAA stays mounted for the shader aliasing MSAA structurally cannot catch
(the reasoning already written in `EffectsImpl.tsx` is correct; only the plumbing was missing).

**Files.**
- **New** `src/scene/aoDepthPrepass.ts` — pure decision + target-allocation helper: given
  `{ multisampling, ao }`, return whether a copied depth target is needed and its parameters.
  Keeps the logic unit-testable, matching `composerPlan` / `mobileMsaaSamples` style.
- **Edit** `src/scene/EffectsImpl.tsx` — wire the copied depth into the `<N8AO>` pass; remove
  the `!ao` condition once verified. Keep `msaaRef` freezing (MSAA-FREEZE) so the composer does
  not rebuild mid-session.
- **Edit** `src/scene/Effects.tsx` — `mobileMsaaSamples()` drops its `ao` exclusion; extend MSAA
  beyond `deviceClass === 'weak'` to `real·capable` once measured. Keep the software-rasteriser
  exclusion (SwiftShader has no tile memory — that reasoning is sound).
- **Edit** `src/features/flags/registry.ts` — flip `mobileMsaa` to `default: true` only after a
  real-GPU verification run.
- **Edit** `src/scene/postStackGuard.test.ts` + `src/scene/composerPlan.test.ts` — add an
  invariant that AO never reads a multisampled depth attachment.
- **Verify** with `scripts/lib/chrome-audit/driver.js` (real GPU) counting
  `GL_INVALID_OPERATION` blit errors per frame — 0 is the pass condition — plus a luma
  comparison at the poses used for the `~20 % mid-tone dimming` measurement. Do **not** accept
  a headless-only green.

**Watch for.** iOS has an *additional*, separate multisample depth/stencil bug
([pmndrs #412](https://github.com/pmndrs/postprocessing/issues/412)) — so ship the fix but keep
an iOS-specific escape hatch, and check whether it moves `z21` BATHROOM-BLACK-BLOB.

### #3 — Ship KTX2/Basis for the lightmaps and the GLB texture set

**Why.** 230 lightmap PNGs currently enter VRAM as uncompressed RGBA through a bare
`TextureLoader`, and no shipped GLB can carry `KHR_texture_basisu` at all because drei's
`useGLTF` never wires a `KTX2Loader`. iOS Safari's WebGL heap is ~300–500 MB and memory is the
top cause of iOS WebGL crashes. A 4–8× texture-memory cut is the difference between "works on a
phone" and "works on a phone reliably" — and it retroactively changes the cost calculus on the
higher-resolution lightmap re-bake that was rejected as too expensive (N8-RES).

**Shape.** UASTC for the lightmaps (they are data-like — banding in an irradiance map is
immediately visible, and the existing `encode 0.5` scale makes them sensitive) and ETC1S for
ordinary albedo. Transcode at load. The transcoder is **already self-hosted** in `public/basis`
and the offline encode path already exists behind a flag.

**Files.**
- **Edit** `src/furniture/gltf/decoders.ts` — the module already documents *why* KTX2 cannot be
  registered at boot (it needs the live context for `detectSupport`). Add a renderer-bound
  registration that runs inside the R3F tree, alongside `src/scene/AnisotropyController.tsx`
  (which already does exactly this pattern for `getMaxAnisotropy()`), and pass a configured
  `KTX2Loader` through the existing `secureGltfLoader` extension hook used by
  `src/furniture/GltfModel.tsx`, `src/ui/glbEditor/DesignerViewport.tsx` and
  `src/ui/catalog/thumbnails.tsx`.
- **New** `src/scene/KTX2Controller.tsx` (or fold into `AnisotropyController.tsx`) — calls
  `detectSupport(gl)` once per context, re-runs on context restore the way
  `AnisotropyController` and `SceneEnvironment` already handle `ContextLossGuard`.
- **Edit** `src/scene/VisibilityLightmaps.tsx:234` — swap the bare `TextureLoader` for a
  format-aware loader with a PNG fallback (offline builds and the Electron/Capacitor packages
  must still work if transcoding is unavailable).
- **Edit** `src/scene/lightmapIndex.ts` — the manifest gains a format field so a mixed
  PNG/KTX2 set is loadable during rollout.
- **Edit** `python/scripts/optimize_glb_lod.mjs` — the `--ktx2` path currently *silently* falls
  back to WebP when `toktx` is missing. Make that loud, and make KTX2 the default for the
  shipped tiers.
- **Edit** the lightmap bake script to emit KTX2 directly.
- **Measure** before/after `gl.info.memory.textures` and the iOS heap; re-test the 1459 ms load
  hitch (`(z)6`) and the 216 ms lightmap-attach compile frame — both are upload-bound and should
  move.

**Watch for.** KTX2 is lossy: run the lightmap set through the existing linear-view luma
comparison before and after and confirm the delta is inside the noise floor already established
by the AgX parity work. A lightmap that shifts 3 counts invalidates the fitted gains.

## 10. Honest list of what is *not* worth it

- **WebGPU migration** — an XL rewrite that deletes `EffectComposer`, every `onBeforeCompile`
  patch (including the lightmap injection that is this app's core feature), drei `Environment`
  and `Text`, for performance gains concentrated in workloads this app does not have.
- **SSR, SSGI, radiance cascades** — all three are either removed from the ecosystem, disowned
  by their author, or WebGPU-compute-only, and all three approximate something the Cycles bake
  already computes properly.
- **TAA on WebGL** — no maintained implementation exists in 2026.
- **Gaussian splatting** — fundamentally incompatible with a configurable interior.
- **Head-bob** — the comfort literature is against it and a showroom gains nothing.
- **Iridescence, dispersion** — no surface in a Singapore HDB flat calls for them.
- **More post-processing polish in general** — the grain/vignette/CA/DoF settings already shipped
  sit exactly where the 2026 archviz consensus puts them ("less is usually more"). This is the
  one area to leave alone.
