## Ranked findings

### M1 — A bottom toast fully hides the walk-mode joystick on portrait phone; landscape escapes it (HIGH)

**State/orientation/standalone:** walk mode, portrait (390×844), **both** tab-like (`tabP`) and
standalone (`stdP`) — does not reproduce in landscape (`tabL`/`stdL`).

**Symptom.** The touch joystick is the app's only way to move while walking —
`docs/user/navigating.md:130` promises "A translucent joystick appears at the bottom-left — drag
it to move." On a 390 px-wide phone, any bottom toast (the update-available/downloading banner
is the one exercised here, but the mechanism applies to any `.toast`) renders **on top of and
across** the joystick's screen position, hiding it completely. If a toast fires while the user is
mid-walk (an update check, a save confirmation, any future notification), the user is left with
no visible way to move — a genuine dead end, not just a cosmetic overlap.

**Evidence.**
- `/tmp/review/mobile/shots/measure/tabP-toasts.png`, `/tmp/review/mobile/shots/measure/stdP-toasts.png` — walk mode entered directly (`setCameraMode('firstPerson')`, no menu ambiguity), then `window.__updateFlow.set({type:'downloading', done:null,total:null})`. The joystick, clearly visible in the preceding `-walk.png` capture of the same run, is **completely absent** from the frame once the toast renders — hidden behind the toast card, not merely occluded at the edge.
- `/tmp/review/mobile/shots/measure/tabL-toasts.png`, `/tmp/review/mobile/shots/measure/stdL-toasts.png` — same state, landscape: the joystick (bottom-left orange circle) remains fully visible and clear of the toast.

**Root cause.** `src/styles/screens.css:263` — `.walk-joystick { position:absolute (fixed under
body.mobile); left: calc(env(safe-area-inset-left,0) + 20px); bottom: calc(env(safe-area-inset-
bottom,0) + 24px); width:88px; height:88px; z-index: var(--z-pop) }` — sits in the bottom-left
corner at `z-index:40`. `src/styles/features.css:549` — `.toast-host { position:absolute; left:
50%; transform:translateX(-50%); z-index: var(--z-toast) }`, with `.toast` given `max-width:
460px` (`features.css:550`) — on a 390 px viewport a centred toast is nearly edge-to-edge, so its
left edge reaches well past the joystick's `x:[20,108]` footprint. `src/styles/tokens.css:100/
102/109` — `--z-hud:10, --z-pop:40, --z-toast:70` — the toast stacks strictly above the joystick,
so wherever they overlap the toast wins the paint, not just the hit-test. On an 844 px-wide
landscape viewport the same ~390-460px-wide toast leaves the far-left corner (where the joystick
sits, offset by the 59px left safe-area inset in `stdL`) clear, so the same code path never
overlaps there — this is a portrait-width-specific geometry coincidence, not an intentional
safeguard.

**Fix hypothesis.** Either (a) give `.walk-joystick` a z-index above `--z-toast` while
`cameraMode === 'firstPerson'` (simplest, matches the promised behaviour — the joystick is a
primary control, not decoration, while walking), or (b) constrain `.toast-host`'s horizontal
placement in walk mode (e.g. inset it from the left by the joystick's width + margin) so a
full-width toast never reaches the joystick's corner. (a) is less invasive and doesn't risk
crowding other walk-mode HUD elements that already anchor top/right.

**DESIGN.md citation:** "Mobile (≤640px `body.mobile`): bottom sheets, ≥44px touch targets,
safe-area insets, desktop/mobile parity for every action" (line 103) — a control that vanishes
entirely is a stronger violation than an undersized one.

### M2 — Landscape phone never gets the mobile layout; it renders the full desktop toolbar and floating panels (HIGH)

**State/orientation/standalone:** every state, landscape (844×390), **both** tab-like (`tabL`)
and standalone (`stdL`).

**Symptom.** `body.mobile` — the class that switches the app to bottom sheets, the hamburger
menu, and ≥44px touch targets — toggles at `(max-width: 640px)` only
(`src/ui/breakpoints.ts:18`). A phone rotated to landscape is 844 px wide, so it is **not**
classified as mobile at all: it gets the same UI a 900px desktop window would, at touch-hostile
sizes. Concretely: the catalog and inspector render as **floating side/top panels with no drag
grabber**, not bottom sheets (compare `shots/tabL/11-catalog-sheet.png`, a desktop-style split
panel, against `shots/tabP/11-catalog-sheet.png`, a correct bottom sheet with a `sheet-grab`
handle); the toolbar is the full multi-icon desktop island rather than a single Menu button
(`03-menu-view` shows `TAP-MISS | Menu` logged three times in the `tabL`/`stdL` reports — there
is no such button to find); and a large fraction of controls sit under the tablet/compact
breakpoints' 34×34–36×34px sizing instead of 44px.

**Evidence (quantified, not just visual).** The `tapTargets` probe count per state, portrait vs
landscape, same script, same states:

| State | `tabP` | `tabL` | `stdP` | `stdL` |
|---|---|---|---|---|
| `02-home-orbit` | 0 | 13 | 0 | 13 |
| `10-room-editor` | 0 | 20 | 0 | 20 |
| `11-catalog-sheet` | 0 (12 overflow, expected scroll) | 40 | 0 | 40 |
| `15-inspector-sheet` | 0 | 35 | — | 0 |
| `22-share-sheet` | 1 | 24 | 1 | 24 |

Screenshots: `shots/tabL/*.png` vs `shots/tabP/*.png` for every numbered state; probe detail in
`/tmp/review/mobile/tabL-report.json` / `stdL-report.json`.

**Root cause.** `src/ui/breakpoints.ts:18` (`MOBILE_MAX_WIDTH = 640`) and the mirrored CSS
literals in `src/styles/responsive.css` (`body.mobile` block, `@media (max-width: 960px)`
"COMPACT" block) key purely on CSS width, with no `orientation` or `(pointer: coarse)` term, so
a touch device simply wider than 640px (any phone in landscape) falls through to
desktop/tablet-scale chrome. This is a real, common orientation for viewing/walking through a
finished room (the brief explicitly asks the audit to test it), not an edge case.

**Fix hypothesis.** Needs a product call on the exact rule (desktop windows can also be short —
an orientation-only or height-only gate would misfire there), but the safest targeted change is
adding a `(pointer: coarse) and (max-height: 500px)`-style clause alongside the existing
width check, so a touch device in landscape still gets bottom sheets and 44px controls while a
short desktop browser window does not. Flagging for the maintainer rather than deciding
unilaterally, per `CLAUDE.md`'s "no src/ changes" for this review pass and the general "don't
decide open graphics/product calls unilaterally" rule.

**DESIGN.md citation:** line 103, same as M1 — landscape phone gets neither the bottom sheets nor
the 44px targets the rule promises.

### M3 — The mobile 44px tap-target rule was applied to catalog chips but not to switches, pet chips, or the onboarding dots (MEDIUM)

**State/orientation/standalone:** Scene menu, portrait, all arms including `swP`; onboarding,
cold start, all portrait arms.

**Symptom.** The app clearly *has* a working mechanism for bumping touch targets to 44px on
mobile — `src/styles/responsive.css:564` and `:584` bump `.catalog .chip` to
`min-height/width: 44px` under `body.mobile`, and it works (no tap-target finding on the
catalog's category chips). But sibling controls in the same menu system never got the same
treatment:
- `.switch` (Lights / Photographic-look toggles) stays a fixed 34×20px on phone width —
  `src/styles/components.css:820`, rendered from `src/ui/toolbar/mobile/SceneSection.tsx:97` and
  `:124` (the dedicated **mobile** Scene section, not a reused desktop component).
- `.pet-chip-row .chip` (Dog/Cat/Bird/Rabbit/… backdrop chips) stays ~24px tall —
  `src/styles/features.css:696`, rendered from `src/ui/PetProfileControl.tsx:27`, with no
  mobile override anywhere in `responsive.css`.
- The "System time · HH:MM AM" button is 282×30 (`SceneSection.tsx`, same menu).

**Evidence.** `/tmp/review/mobile/tabP-report.json` / `stdP-report.json` / `swP-report.json`,
state `04-menu-scene` / `05-menu-scene-again`: 11 `tapTargets` findings each run, all switches/
chips/the time button. Screenshot: `shots/tabP/04-menu-scene.png`.

**Fix hypothesis.** Extend the same `body.mobile` media-query treatment already proven on
`.catalog .chip` to `.switch` and `.pet-chip-row .chip` (bump to 44px min tap area, keep the
visual thumb/label small via padding rather than resizing the whole visible pill if the smaller
look is wanted).

**DESIGN.md citation:** line 103, "≥44px touch targets" for `body.mobile`.

### M4 — Onboarding progress dots are real 7×7px buttons with no visible affordance (LOW)

**State/orientation/standalone:** cold start, onboarding carousel, portrait.

**Symptom.** The three dots under the "Welcome to Sofa So Good" card
(`shots/cold/c01-onboarding-1.png`) look like a plain, non-interactive step indicator, but they
are real `<button class="onb-dot">` elements (`src/ui/Onboarding.tsx:218`,
`src/styles/flows.css:106`: `width:7px; height:7px; ... cursor:pointer`) — about 1/6 of the 44px
minimum, and the very first control layer a cold-start user meets.

**Evidence.** `/tmp/review/mobile/cold-report.json`, states `c01`–`c03`: 3 `tapTargets` findings
each (7×7 or 8×8px). Impact is low because the primary navigation (Skip / Next / Get started
buttons, all correctly ≥44px) doesn't require using the dots.

**Fix hypothesis.** Either bump the hit area with invisible padding (`::before` with a larger
tap box, common pattern for small indicator dots) or drop the `cursor:pointer`/button semantics
if they were never meant to be tappable and let them be pure decoration.

### M5 — A Scene-menu sub-label clips by 6px even with an ellipsis (LOW, cosmetic)

**State/orientation/standalone:** Scene menu, portrait, `tabP`/`stdP`/`swP` (not `tabL`/`stdL`,
which have more width).

**Symptom.** "Animate fan blades and other moving furniture" (the Motion toggle's sub-label,
`src/ui/toolbar/mobile/SceneSection.tsx:156`) truncates with an ellipsis at `scrollWidth 219 >
clientWidth 213` — a 6px overflow, i.e. it's clipping right at the edge of fitting.

**Evidence.** `04-menu-scene` / `05-menu-scene-again` probes, all three affected arms:
`{"kind":"clipped-text","el":"span.m-item-s","detail":"scrollW 219 > clientW 213"}`.

**Fix hypothesis.** Trim the copy by a word ("Animate fan blades & other furniture") or give the
sub-label row a few more px of column width; cosmetic, not worth more than a one-line copy edit.

## False leads chased down and ruled out (do not re-check)

1. **"Camera stuck in first-person after exiting walk mode"** — `CAMERA-AFTER-EXIT` fired in 4 of
   5 `-report.json` files (`{"cameraMode":"firstPerson","walkHud":true}`), and states 21–25 in
   those runs (`shots/{stdP,tabL,stdL,swP}/21..25-*.png`) all show a first-person view, not the
   intended orbit/share/cmdk/checklist context. Root-caused with two targeted repro scripts
   (`/tmp/review/mobile/walkexit3.mjs`, `walkexit4.mjs`): the harness's fuzzy label matcher
   (`tapLabel('Orbit')`, substring `includes()` over all buttons in DOM order) matches the
   always-present `"Return to orbit mode"` brand-dot logo (top-left, present in the DOM before
   the dropdown even opens) instead of the View-dropdown's actual "Orbit" menu item; the tap then
   lands on the dropdown's own closing backdrop and does nothing. A precisely-scoped test
   (`/tmp/review/mobile/verify.json`: `walkItem`/`orbitItem` located via `.m-item`,
   `afterOrbitTap: {"cameraMode":"orbit"}`) confirms the real "Orbit" menu item exits cleanly and
   instantly, no confirmation needed. Separately, tapping the brand-dot logo directly **does**
   show a "Return to orbit mode?" confirm dialog (`shots/verify/r11-after-brand-tap.png`) —
   correct, deliberate `confirmAction()` behaviour for that shortcut, per DESIGN.md's
   confirmation policy. Net: no product bug, but a harness lesson (scope label matches to a
   specific menu/dropdown root, never all buttons on the page) and it means states 21–25 in 4 of
   5 arm reports were captured in the wrong camera mode — `25-checklist` shows no checklist in
   any arm because the widget only renders outside walk mode, not because it's missing.
2. **Two update-flow toasts stacked simultaneously** (`shots/tabP/24-update-downloading.png`
   shows "New version available" AND "New version — downloading…" at once) — caused by the audit
   script driving stages out of their real order (`ready` before `downloading`, plus an invalid
   `{type:'failed', message:...}` stage the state machine doesn't recognise — the real terminal
   type is `error`/`msg`). `src/pwa/swUpdate.ts:432-508`'s `devToastId` liveness tracking
   explicitly replaces the live progress toast in place stage-to-stage (comment: "mirroring
   `runUpdateCheck`'s own `notify.dismiss(id)`... so a scenario driving these stages one after
   another sees the same single-toast UX a real check produces, not several toasts piled on
   top"); the stacking only happens when stages are driven in an order production code can't
   produce. Not a product bug — a test-script bug in the harness under review.
3. **`div.bud-seg` reported "offscreen-x"** during the update-downloading toast — this is the
   toast's own indeterminate progress-fill (`.bud-bar.indet .bud-seg`,
   `src/styles/features.css:597`, a `1.1s infinite` slide animation) caught mid-loop; sliding
   edge-to-edge is the intended indeterminate-progress look, not a layout bug.
4. **Catalog category chips reported "offscreen-x"** (Storage/Kitchen/Bathroom/Appliances/… past
   the visible width, both portrait and landscape) — `src/ui/catalog/CategoryTabs.tsx` renders an
   intentional horizontal-scroll rail (`railRef`), not a fixed row; the chips are reachable by
   scrolling the strip, not clipped off. The probe's `getBoundingClientRect()`-based overflow
   check doesn't know about scroll containers, so this reads as a false positive for any
   scrollable row — worth remembering for future probe runs.

## Looks right

- Portrait bottom sheets (catalog, inspector) reflow correctly with a visible grab handle, and
  the catalog's own category chips are correctly bumped to 44px on mobile
  (`responsive.css:564,584`) — proof the design system's mobile-sizing mechanism works when it's
  wired up.
- Standalone-mode safe-area handling holds: `shellH = innerH + top-inset` exactly (903 = 844 + 59
  in `stdP`), not double-counted — the MOBILE-CHROME-2 fix (v0.35.1.3) is still correct — and the
  bottom-anchored overlays it specifically fixed (`toast-host`, `budget-hud`, `drag-readout`,
  `walk-joystick`, `walk-hud-dock`) are still `position:fixed` and correctly clear the home
  indicator in every capture.
- The catalog-sheet drag (360 frames/6.665s, ~54 fps) and the walk joystick drag (313
  frames/5.249s, ~59.6 fps) both recorded **zero `STUTTER` events** (rAF delta > 120ms) on
  `phone-metal`; the only flagged events were an expected single `DPR_TOGGLE` (documented in
  `docs/interaction-sweep.md` as "expected, not a defect" — that's `interactiveDegrade` doing its
  job) and 47 `POP` events on the sheet drag that turn out to be the sheet's own slide boundary
  crossing tile boundaries in a smooth, monotonic sequence (tile position marches one step every
  ~50ms) — the `POP` gate assumes camera stillness means no legitimate motion, which doesn't hold
  for a 2D sheet drag over a static 3D view; not real jank.
- The real walk-mode exit path (View menu → Orbit) and the brand-dot shortcut's confirmation
  dialog both work correctly (see false lead #1) — no actual dead end in walk-mode exit.
- Cold-start onboarding (3-step carousel), start-choices, and the Get-started checklist all
  render without overflow or clipping across every arm tested.
- No `contrast` probe finding fired in any of the ~150 states/screens captured.
