# Security review — round 7 (R7-W), 2026-09-25

**Reviewed head:** `42f874cf` (v0.35.17.9) on `feat/photoreal-round7`, range `2f621182..42f874cf`.
Later pushes (weather, the reduce-motion CSS bridge, room-probe lifecycle) are **not** covered.

**Method:** a static read of every round-7 file with attack surface, plus throwaway Vitest
probes (happy-dom, deleted afterwards and never committed) that drove the real
`decodeDesignShareCode` / `loadSharedDesignFromUrl` / `onShareRouteChange` / `startAutosave`
code. One `vite build` into `/tmp` to check what ships in the bundle. No browser, no dev
server. I ran `npm audit` and traced the reachability of each advisory.

**Threat model** (from the brief): a local-first static site with no server in the core loop.
Findings are ranked by (1) a malicious or careless **share link** sent to a victim, (2) a
malicious asset, (3) supply chain, (4) leakage of the user's own data or keys. Two things are
known and accepted, so they are not reported here: (a) client-side view-only is a UX
affordance, and (b) showroom visitors can reach `aiPhotoreal`. Separately, sender location does
not travel in links (`buildDesignSharePayload` sets `location: null`), and that is not re-raised.

**Labels:** CONFIRMED means traced in code *and* reproduced by a unit probe, or verified by
file inspection. PLAUSIBLE means the mechanism is real but the impact needs a runtime (GPU or
browser) to prove.

---

## Verdict

**One finding should block a staging-to-main merge of the showroom feature (S1).** It is not
a breach, since nothing leaves the device and there is no code execution. It is a data-loss
bug that any showroom link triggers, even a harmless one. It directly contradicts the
feature's own documented invariant, and the fix is small. Everything else is either
hardening or a documentation correction.

The share-link parsing pipeline is **clean**. Decompression is genuinely bounded. `__proto__`
keys are dropped by zod and cannot pollute. No link-derived string reaches an HTML, `eval`
or URL sink without escaping or allow-listing. The dev hooks, including `window.__shareHash`,
are absent from a production build. Under this threat model, the worst a malicious link can
do is S1 (overwrite the victim's work) and perhaps S2 (a heavy scene that S1 then makes
sticky). It cannot run script.

|---|---|---|---|
| S1 | Opening a showroom link overwrites the visitor's own autosave, and its cloud mirror, with the sender's design | **CONFIRMED** | **High (block)** |

## S1 — A showroom link overwrites the visitor's own design (CONFIRMED, High)

**Where**
- `src/state/storage/bootstrap.ts:259-262`: `loadSharedDesignFromUrl` does
  `useStore.setState(patch)` with the sender's design, then `clearHistory()`. There is no
  confirmation and no snapshot of the visitor's current design.
- `src/state/storage/autosave.ts:247-258`: the autosave subscriber has **no `viewOnly`
  guard**. Any change to a watched field schedules `serialize(state)` into `AUTOSAVE_SLOT`.
- The watched fields that a showroom visitor is *allowed* to change include `timeMode`,
  `manualHour`, `weather`, `lightsMode`, `lightMood`, `cameraMode` (walk mode), `items`
  (walk-HUD curtains and lights write `item.props`) and `designNote` (the ungated Share-modal
  textarea). See `docs/developer/showroom-links.md` lines ~270-282.
- `src/state/storage/adapter.ts:65`: for a signed-in user on a backend build (production
  `main`), `AUTOSAVE_SLOT` writes are mirrored to the cloud (`scheduleAutosavePush`), and
  `cloudBoot` reconciles latest-wins across devices.
- `src/state/storage/bootstrap.ts:308-352`: round 7's `installShareRouteListener` extends the
  same overwrite to a **live** tab. A same-document hash change to `#/design/…` or
  `#/showroom/…` replaces the in-progress design and clears undo.

**Reproduced (probe):**
1. The visitor has the 87-item default flat.
2. They open a 1-item `#/showroom/<code>`, so `viewOnly === true`.
3. They move the time of day.
4. After the 500 ms debounce, the autosave adapter received **1 item**.

Probe P2 got the same result through `onShareRouteChange` in a running session.

**Attack or accident scenario:** Alice has spent a week furnishing her flat. She has no named
save slot, which is normal, because autosave is the primary persistence. A friend (or a
griefer) sends "look at my showroom" as a `#/showroom/…` link. Alice opens it and switches
to walk mode to look around. That write replaces her autosave. Undo was cleared on load. If
she is signed in, the sender's design is pushed to her cloud slot and reaches her other
devices on their next boot.

Later she opens the app from her home-screen icon (`start_url: "."`, no hash). She boots
into the sender's design as an ordinary **editable** design, and her own work is gone. So
the view-only boundary does fail open into persistence. The `viewOnly` *flag* never leaks,
as the docs say, but the showroom *content* becomes the visitor's own editable autosave.

**Why this is round 7's problem, not a pre-existing one:** `#/design/` links (C224) already
replaced the local design without confirmation, but that is framed as "it's yours to edit".
The showroom route is presented to both parties as **view-only**. The developer doc says
that walk interactions are "not persisted anywhere the sender can see" and that `designNote`
is "session-local". Both are true only in the narrow sense that nothing reaches the
*sender*. Both are false for the visitor's own storage. The reactive listener is also new in
this round.

**Suggested fix (not applied):**
- Skip autosave scheduling while `viewOnly` is true: `if (useStore.getState().viewOnly) return`
  in the subscriber, and resync `lastPersistent` when leaving via `takeEditableCopy`.
- Optionally, snapshot the visitor's pre-link design into a recoverable slot before applying
  any shared design. That covers `#/design/` too.
- Add a unit test that asserts no `AUTOSAVE_SLOT` write happens in a showroom session.

## S2 — No item-count ceiling on a shared design (PLAUSIBLE, Medium)

**Where:** `src/state/schema.ts:615` (`items: z.array(FurnitureItemZ)`, with no `.max()`),
`src/features/designShare.ts:33,39` (16 KB code, 4 MB inflate cap) and
`src/features/planShare.ts:50,57` (the `#/plans/` route allows a **2 MB** code and a 50 MB
inflate).

**Measured (probe):** a 16 KB `#/design/` or `#/showroom/` code decodes and validates to
**2,856 items with unique IDs** (27 ms) or **6,272 items with duplicate IDs**, all
referencing a built-in def, so none are dropped as unknown. The `#/plans/` route's 2 MB
budget allows roughly 100x that.

**Scenario:** the victim opens a crafted link. The tab tries to mount thousands of furniture
instances, which could be a multi-second hang, a WebGL context loss, or an OOM on mobile.
Because of S1, one incidental watched-field write persists the payload, and for a showroom
link the hash is kept anyway. Every later boot then re-hydrates it, and the only recovery is
clearing site data.

The actual render cost at 3–6k instances is **unproven**, because a GPU run is needed, hence
PLAUSIBLE. Fixing S1 removes the stickiness. A schema ceiling such as `.max(2000)` on
`items` (well above any real flat) would remove the rest.

## S3 — Stale lightmaps can outlive a version bump (CONFIRMED, Medium, integrity)

**Where:** `vite.config.ts:146-157` adds a `CacheFirst` runtime cache,
`lightmap-png-fallback`, with a 90-day expiry. The comment justifies it with "Content-digested
filenames, so CacheFirst can never serve a stale map."

**That claim is false.** Map filenames are `<plan-context digest>-<geometry key>`
(`src/scene/lightmapIndex.ts:2-41`: a hash of world-space vertices, not of the pixels). A
re-bake of the same geometry keeps the filename. This has already happened twice in
history: `bb96e7ca` (SUN-BOUNCE-BAKE, v0.35.1.0) and `4007f380` (LIGHTMAPS-DENOISED,
v0.35.8.0) both modified `public/assets/lightmaps/*.png` in place.

The UPDATE-FLOW purge does not cover this cache either. `src/pwa/cachePurge.ts:34-38`
(`RUNTIME_CACHE_NAMES`) lists only `shared-library-assets`, `user-guide` and
`remote-cc0-assets`. The sync guard in `src/pwa/cachePurge.test.ts:16-21` only checks
*listed ⊆ config*, not *config ⊆ listed*, so a newly added cache slips through silently.

**Scenario:** this is the same shape as the earlier stale-install incident, not an attack.
Take a device whose KTX2 transcode fails (the C3 fallback population). The next re-bake
ships new PNG bytes under the same names, and that device keeps rendering the old baked GI
for up to 90 days across any number of app updates. It is visually wrong and invisible to
the user. It needs no attacker. Poisoning the cache would need control of the same origin
over HTTPS, which is out of model.

**Suggested fix (not applied):**
- Add `'lightmap-png-fallback'` to `RUNTIME_CACHE_NAMES`.
- Make the sync test bidirectional by parsing every `cacheName: '…'` in `vite.config.ts`.
- Correct the comment, or put a content hash or bake ID into the URL
  (`index.json` is already fetched `no-cache`).

## S4 — A failed decode leaves `viewOnly` stale (CONFIRMED, Low)

**Where:** `src/state/storage/bootstrap.ts:254-290`. `setViewOnly` runs only on the success
path. The hash-clearing decision in `finally` uses the *local* `viewOnly`.

**Reproduced (probe P6):** in an editable live session, a hash change to
`#/showroom/<garbage>` shows an error toast and leaves `viewOnly === false`, but **keeps**
the `#/showroom/…` hash. The reverse also happens. A showroom session that hops to a broken
`#/design/…` stays gated, while the hash is cleared through `replaceState`, which fires no
`hashchange`.

**Impact:** URL and session disagree. No sender content is exposed, because nothing was
loaded, so the fail-open direction protects nothing. This contradicts the
`designShare.ts:69-71` comment that "the route alone is enough to enter view-only mode".
Worth a line: set `viewOnly` from the route in the `catch` as well, or document the
exception.

## S5 — `beforeinstallprompt` accepts untrusted events (CONFIRMED, not exploitable)

**Where:** `src/pwa/installPrompt.ts:86-93` (raised in R7-O).

**Assessment: untidy, not exploitable.** Only script already running in this origin can
dispatch a synthetic `beforeinstallprompt` on `window`, and that script has already won. A
synthetic `Event` has no `prompt()`, so `promptInstall()` throws, is caught, and returns
`'unavailable'` (`:129-132`). The worst outcome is the install card appearing when no real
prompt exists. The native install dialog is browser chrome and cannot be spoofed through
this path. Adding `isTrusted` is fine hygiene. It is not a security fix.

## Areas checked and found clean

**Decompression bounds.** `inflateBounded` (`planShare.ts:65-87`) streams 16 KB slices and
aborts at the cap. Probes:
- A 60 MB bomb is rejected at the code-length pre-check in 0 ms.
- A **13.6 KB** code that inflates to 10 MB (it fits the 16 KB budget) is aborted at the
  4 MB cap in 35 ms.

**Prototype pollution.** I injected own `__proto__` keys into `doors`, `finishes.floor` and
`items[].props`. Zod 4 drops them, the output prototype stays `Object.prototype`, and there
is no global pollution. `constructor` survives only as an inert own string property. In
`applySerialized`, `validRoom(k)` uses `k in ROOMS` (`schema.ts:977`), which is true for
inherited names like `toString`, but it only ever *assigns* a string, so there is no impact.

**Zod stripping.** `viewOnly` is read off the raw envelope before validation and only the
literal `true` counts (`designShare.ts:149-153`). It is not in `serialize()`, the autosave
watch-list or exports, so the flag itself cannot persist. See S1 for the content.

**HTML, URL and eval sinks.** Round 7 adds no new sink. Link-derived strings shown in round-7
UI (room names in `OrbitRoomReadout`, `ShowroomBadge`, toasts) are React text. The export
writers a visitor can now reach (`report`, `moodboard`, `shoplist`: `document.write` into a
pop-up) escape with the 5-character `escapeHtml`, and product links go through `safeUrl`
(http, https and mailto only). Item-meta links go through `validateItemUrl`. Share URLs are
built from `location.origin` + `BASE_URL` + a `[A-Za-z0-9_-]` code.

**`window.__shareHash` and the other dev hooks.** These are installed only inside
`if (import.meta.env.DEV)` (`bootstrap.ts:190`). A production `vite build` contains **zero**
occurrences of `__shareHash`, `__store` or `__arrangeRoom`.

**KTX2.** The transcoder path is build-time only (`VITE_KTX2_TRANSCODER_PATH` or
`withBase('/basis/')`). `public/basis/basis_transcoder.{js,wasm}` are **byte-identical**
(SHA-256) to `three/examples/jsm/libs/basis/`. The blob worker is three's own, built from
same-origin transcoder text. Lightmap URLs come from the same-origin `index.json`, with
format and extension cross-checked (`lightmapIndex.ts:231-263`). No asset path is influenced
by a share link. A GLB's `KHR_texture_basisu` still passes through SEC-1's
`secureGltfManager`, because `attachKtx2Loader` only adds the loader.

**PWA.** The manifest uses a relative `start_url` and `scope` with no third-party origins.
The update path in `swUpdate.ts` is unchanged in round 7. It still prompts rather than
auto-reloading, and `cleanupOutdatedCaches` handles the precache. The only new cache is S3.

**Replicate BYO key (`src/ai/aiClient.ts`, unchanged in round 7).**
- The key lives in `localStorage['hdb_ai_key']`. It is never in `serialize()`, share
  payloads, exports or the cloud sync (no reference outside `aiClient.ts`).
- It is sent only as `authorization: Token …` to `https://api.replicate.com`. The poll URL
  is origin-pinned (`safePollUrl`), so a tampered `urls.get` cannot redirect the key.
- Error strings are generic and never include the key.
- Egress is the rendered PNG data URL plus the style prompt, sent to Replicate only. Nothing
  else from the design is sent.
- Hardening note (pre-existing): the returned output URL is used as an `href` without
  `safeUrl` (`AiPhotorealSection.tsx:224`). It is only reachable via a Replicate response,
  so it is low risk. Also, the app ships **no CSP**, so any future XSS would read this key.
  A CSP is worth adding at some point.
