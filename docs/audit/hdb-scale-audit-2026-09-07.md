# HDB scale audit — 2026-09-07

Is the default 4-room flat **accurate, precise and to scale**? Every dimension a Singaporean
viewer would read as wrong, checked against the published HDB / BCA / SCDF / PUB standards for
a 2000s-era 4-room BTO-type flat.

**Scope:** the default `Serangoon North Vista` 4-room plan only, and its **shell, fittings and
environment** — not furniture (that catalogue is IKEA-sourced and out of scope; its dimensions
appear below only as context rows marked *furniture*).

**Three columns, three different sources, deliberately.**

- **code** — the constant, with `file:line`.
- **measured** — read back out of the *rendered scene* by
  [`scripts/dev-probes/scale-audit.mjs`](../../scripts/dev-probes/scale-audit.mjs), which is
  re-runnable and asserts every row it signs off. A constant can be right while the mesh built
  from it is wrong, and that is not hypothetical: the first pass of the blast-door fix corrected
  `wallSegments`' solid spans and the door leaf and left `buildWallBodyOutline`'s extruded hole
  at 2.1 m, which the probe caught as `0 → 2.09` when the leaf was already 1.9 m.
- **reference** — a value quoted from a document that was **fetched**, with its URL. Per the
  root `CLAUDE.md` rule, none of this is recalled.

```
URL=http://localhost:5200/ node scripts/dev-probes/scale-audit.mjs            # corrected
FLAG=off URL=http://localhost:5200/ node scripts/dev-probes/scale-audit.mjs   # pre-audit
```

Corrections ship behind ONE flag, **`hdbScaleAudit`** (`tier: 'simple'`, default **on**);
`src/apartment/hdbScaleAudit.ts` is the resolver and carries each citation at the constant.
With the flag off every pre-audit dimension returns exactly.

---

## How to read the verdicts

| verdict | meaning |
| --- | --- |
| **ok** | Code, mesh and reference agree (or the reference is a range the value sits inside). |
| **fix** | A pure dimension error against a specific cited clause. Corrected behind `hdbScaleAudit`. |
| **product call** | The reference and the modelled value genuinely conflict, or the reference straddles the value, or the value is traced from the source floor-plan asset. **Not** changed here. |
| **note** | A measured observation worth recording that is not a dimension error. |

**S12 root cause (chased separately from this audit, HDB-SCALE-AUDIT-S12, no `hdbScaleAudit` flag needed — a pure correctness fix).** `wallCornerJoin` (`src/apartment/wallSegments.ts`) classified ANY "mutual" wall-end pair — both walls terminate at the same point — as a true L-corner needing a 45° mitre, without checking whether the two walls actually turn to a different axis. `wall-ext-N-east` (200 mm) starts exactly where `wall-ext-N-pier` (300 mm RC, `constants.ts:364`) ends — both run along the SAME line (the north wall), split purely for the pier's own structural classification, not because there is a real corner there. That false "mitre" fed `wallCornerMiter` a nonzero diagonal slope (`tNb/tThis × sign = 1.5`), and `wallBodyGeometry.ts:applyMiter` shears **every** vertex on the wall's start half — including the B3 window hole's near jamb, whose declared offset is only 0.04 m from that same start (`constants.ts:385`, "re-based to this wall's own start"). At the wall's own interior-facing thickness plane the shear clamped the hole's left edge inward by ~0.10 m (`-1.0825 → -0.9825` in the wall's centred along-axis frame), landing on the measured 1.38 m; the other jamb face was unaffected (clamp only bites on ONE side of the diagonal), so the 1.38 m the raycast reported was a real, single-face geometry defect, not a probe artefact. Confirmed with a throwaway `tsx` script exercising the production functions directly (`wallCornerJoin`/`wallCornerMiter`/`buildWallBodyOutline`) before touching any code, then fixed by adding a collinearity check: a mutual end whose neighbour runs along the same axis (cross product of unit directions ≈ 0) now returns `{ kind: 'butt', abut: 0 }` — the two segments were authored to meet with zero gap already, so there is no notch to fill and nothing to shear. Verified: `scale-audit.mjs` now reports `win-bedroom3-N` at **1.48 m**, byte-identical everywhere else in the table (diffed the full before/after report — only that one line changed); `wallSegments.test.ts` gained a synthetic collinear-pier unit test plus an end-to-end test that rebuilds `wall-ext-N-west`/`wall-ext-N-east`'s real geometry through the actual pipeline (`wallCornerMiter` → `buildWallBodyOutline` → `extrudeWallBody`) and asserts both windows build to the same clear width — both fail against the pre-fix code (reproducing 1.38 vs 1.48 exactly) and pass after. GPU frames at the `pose-bedroom3` walk pose (`photoreal-defect-sweep.json`) show the fix: the left reveal (nearest the pier) was visibly wider than the right before the fix — the wall was eating into the frame's rightful space — and now reads the same width as the (unaffected) right reveal, with the frame/grille filling the corrected opening. Two other collinear structural splits in `constants.ts` (`wall-ext-E-col1`/`-mid`/`-col2`) shared the same latent mis-classification but carry no cutouts near their shared ends, so they were geometrically wrong (spurious body overlap into the neighbour pier, a latent double-fade-translucency risk) but never visibly wrong; the fix corrects those too, with no opening to regress.

## Reference caveats worth carrying forward

- **Code vintage.** Every accessibility figure above is from the 2019 or 2025 Code. A 2000s BTO
  was built under the 1995/2002 *Code on Barrier-Free Accessibility*, which had **no
  residential-unit chapter at all** — COA Chapter 7 (in-unit entrances, the 850 mm / 1000 mm
  figures, the mandatory 450–1200 mm outlet band) is a later addition. The 850 mm door and the
  900–1100 mm handle are stable across editions and safe to lean on; do not attribute Chapter 7
  clauses to a 2000s flat as as-built requirements. This is precisely why F1 is a product call
  and F7 is a fix.
- **HDB publishes almost nothing dimensional.** Every `hdb.gov.sg/-/media/*` PDF 404s to normal
  fetching (the working paths are `/managing-my-home/...`, with the renovation-guideline text in
  embedded JSON rather than rendered HTML). HDB's own numbers used here are the skirting cap
  (100 mm), the false-ceiling clearance (2.4 m), the pelmet clearance (2.1 m), the partition
  module (63 mm) and the window cill (1.0 m, from the HDB(ARCH) technical requirements PDF).
- **Two premises worth correcting for future work.** **SS 638** (the electrical code, a
  re-designation of CP 5:1998) contains **no general mounting-height clause** — the heights are
  BCA's, not SS 638's; its nearest hook is cl. 132.12 "Accessibility of electrical equipment",
  with no mm. And **SS 553** is the ACMV code, whose scope excludes residential.
- **Genuine gaps, no citable value found:** cornice profile in mm, shower-mixer AFFL for
  Singapore, bib-tap and angle-valve heights, TV/RJ45 mounting height, storage water-heater
  AFFL, bathroom wall-tile extent (full height vs 2.1 m), and HDB's own BTO floor-tile size.

## Re-running

The probe measures the bare shell for openings/trim (it clears furniture first — a curtain over
a window pollutes the band) and the furnished flat for fittings (they are derived from placed
fixtures). Openings are measured by **raycasting through the wall**, not from bounding boxes: a
hole has no mesh, and the extruded wall body's AABB is the full storey however it is punched.
Under `FLAG=off` the four correction rows are *expected* to fail — that is the flag-off arm
reproducing the pre-audit dimensions.
