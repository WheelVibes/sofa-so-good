## Method

Puppeteer + `--use-angle=metal` (real GPU) for `desktop-metal` (1200×900, DPR 1, `isMobile:false`,
device class **pinned** `capable`) and `phone-metal` (390×844, DPR 3, `isMobile:true`, device
class pinned `weak`); a `swiftshader-structural` arm (1200×900, `--use-angle=swiftshader`) for
structure only. `setDeviceClass` is replaced with a no-op after one call, same adaptive-ladder
gotcha as every other probe in this arc — otherwise the ladder walks the tier out from under a
mid-run measurement.

**Two different numbers are reported per pose, and they answer different questions** (the trap
`frame-time.mjs`'s own header note exists to flag): `raf` is the raw `requestAnimationFrame`
timestamp spacing — under `frameloop="demand"` the browser ticks at the **display rate**
whether or not r3f actually renders, so this is a tick-cadence ceiling, not a cost measurement.
`render` wraps `gl.render` itself and buckets the summed duration per rAF tick that actually drew
a frame — this is the real CPU submit cost per DRAWN frame, and `renderHz`/`rafHz` report the
achieved rates so a gap between the two (frames ticking but not drawing, or ticking slower than
60 Hz) is visible instead of hidden. Both series run **concurrently** with whatever gesture the
pose calls for (orbit drag / touch look-drag), not before it — sampling a drag that already
finished would silently re-measure "idle". Window: `min 300` rAF samples or `12 s`, whichever
comes first (SwiftShader needs the timeout escape hatch — see §7).

**The scene is never fully static (a real caveat, not a bug).** The default flat's ceiling fan
animates continuously and calls `pulseShadowRefreshForMotion()` every frame it moves
(`src/furniture/primitives/CeilingFan.tsx`) — `shadowRefreshSignal.ts`'s own docstring names this
as the deliberate exception to PERF-MAX-1's freeze ("continuous furniture animations … covered
separately"). So "orbit boot framing idle" here means *camera-idle*, not *content-idle*: the sun's
shadow map legitimately re-renders every frame the fan is in the scene, by design. `shadowSets`
below counts **signal pulses** (a property-setter hook on `light.shadow.needsUpdate`), which fires
regardless of whether that light's `castShadow` is even true — on `performance` tier
`shadowMapSize` is `0` and `castShadow={shadowMapSize > 0}` (`Lighting.tsx:502`) is `false`, so the
602-per-window pulse count on that tier is a **free** signal write, not 602 real GPU shadow
re-renders; treat the column as meaningful cost only on `realistic`.

Kitchen pose: `roomShell('kitchen').center` (`src/apartment/roomShellGeometry.ts`), eye height
1.6 m, looking toward +X — not a hand-placed screenshot pose, so it is reproducible from the room
graph rather than a hardcoded coordinate.

## 6. Phone-specific

**DPR at rest vs mid-gesture** (`performance` tier, 20 s scripted walk: touch look-drag → held
`W` → touch look-drag): `dpr` stayed pinned at **1** throughout, **zero** degrade transitions.
Consistent with §1's phone table — at `performance` tier the render cost (4–6 ms) never

correctly never arms. It DOES arm on `realistic` (§1's 3→1.5, 2→1.5 dpr drops during drags) —
tier-dependent, not device-dependent, and both directions are correct per `MOBILE-POLISH`.

## 7. SwiftShader structural check (desktop, `performance` tier, hour 13:00, lights off)

Timing is **not** meaningful here (CPU rasteriser); only structure, cross-checked against the
Metal desktop-metal `performance` row above:

| pose | calls | tris | programs | tex | lights |
| --- | --- | --- | --- | --- | --- |
| orbit-idle | 2330 | 537,782 | 172 | 85 | 2/0/0 |
| walk-kitchen-idle | 2042 | 487,722 | 197 | 86 | 1/0/0 |

Draw calls and triangle counts are **byte-identical** to the Metal `performance` rows (2330/2042
calls, 537,782/487,722 triangles) — the renderer submits the same geometry regardless of backend,
exactly what "structure only" should confirm. Program counts differ (172/197 vs 160/187) because
this session's boot state carried a different program cache history (SwiftShader's own boot
compiled `144` programs against Metal's `95` before either pose ran — see §5 — so the two arms
never shared a comparable starting cache); the DELTA between the two poses in this arm
(`172→197`, **+25**) is the number that matters and lines up with the walk-switch churn measured
on Metal (§3, +27), same mechanism, cross-backend.

## Checked, no defect found

- **Shadow map resolution never exceeds its tier cap.** `shadowMapSizeForExtent` (`shadowFrustum.ts:132`)
  returns `0` outright when `tierMax <= 0` and otherwise clamps with `Math.min(tierMax, pow2)` —
  structurally incapable of exceeding the tier ceiling regardless of plan extent. No live texture
  was found above its cap in either the shadow map or IBL probe (`envResolution` 64/96/192/256 per
  tier/device — all small, no upload path bypasses `resolveQuality`).
- **`gl.render` per-frame allocation:** the wrapped submit path shows no growing per-call
  overhead across a pose's 300-frame window (`render.p50` stays flat pose-to-pose at a fixed
  tier/scene state — no upward drift within a window that would indicate an accumulating
  allocation in the render hot path).

## Ranked findings

### P1 — `realistic` tier, walk mode, lights on at 21:00: main-thread frame drops for several
seconds after the switch, though per-frame GPU submit cost stays in budget (desktop-metal)

> **ATTRIBUTED AND FIXED, 2026-09-25 (v0.35.12.3) — see
> [`perf-trace-2026-09-25.md`](./perf-trace-2026-09-25.md).** A CDP `Tracing` capture put 45 % of
> the main thread in one `getImageData`: `statusBarTint.ts`'s live `<meta name="theme-color">`
> sampler does a `drawImage(webglCanvas)` + `getImageData` pipeline sync whose cost is the GPU
> queue depth (0.2 ms lights off, **76 ms** lights on) at a fixed 10 Hz. Long-task time in steady
> state 5118 ms → **0 ms** per 8.5 s window. The GC hypothesis below was **wrong**; the residual
> 30 Hz is GPU-bound and is a separate open item. The two "candidates worth profiling next" named
> below were not the cause and were not changed.


**Evidence.** §1, desktop-metal `realistic/walk-lights-on-21:00`: `renderHz` **60.2 → 42.3**
(a ~30% drop in achieved frame rate) and `raf` pacing p90/p99 jump to **50 ms** (3× the 16.7 ms
budget) — while the `render` bucket (actual `gl.render` CPU submit time) stays **12.9–15.6 ms**,
comfortably under budget. Program churn for this exact switch was small (**+3**, `349→352`),
ruling out shader compilation as the cause. The sample window starts 1.5 s after the switch action
and runs up to 12 s, so the stall is not confined to the instant of the click — it persists into
the steady state.

**Reproduces on phone too, more mildly:** phone-metal `realistic/walk-lights-on-21:00` shows
`raf max` **33.3 ms** (one dropped frame, not the desktop's sustained ~10% drop-rate) with
`render` again in-budget (10.0–13.9 ms) — same shape, smaller magnitude, consistent with the
lighter phone content set (fewer materials revalidated by the 19-light mount).

**Fix hypothesis (not applied — see below).** Turning lights on at night mounts 19
`FurnitureLights` point lights in one React commit (`src/scene/lighting/FurnitureLights.tsx`) —
a large tree diff plus the associated allocations (heap grew **+35 MB** desktop / **+18 MB**
phone across this exact step in §4) is a plausible GC-pressure explanation: intermittent
30–50 ms pauses spread over several seconds after a large allocation spike is a textbook GC
signature, not a render-path cost (which the `render` column already clears). Two candidates
worth profiling next: (a) whether `FurnitureLights`' `active` list (`useMemo` at
`FurnitureLights.tsx:98`) recomputes on every render of some unrelated parent during the settle
tail, and (b) whether the 19 lights' own shadow/helper object allocation could be pooled instead
of created fresh per mount.

**Why this was NOT fixed this pass.** The `render` (GPU submit) column being in-budget while
`raf` pacing is not means the stall is outside the one function this pass's instrument can see
inside (`gl.render`) — attributing it to a specific line would need a Chrome performance trace
(main-thread flame chart), which this headless pass did not capture. Shipping a speculative fix
(e.g. deferring the light mount, memoizing something not proven to be the cause) without that
trace risks moving the stall rather than removing it — exactly the failure mode
`src/scene/CLAUDE.md`'s own "measured, not assumed" rule warns against. Left as a ranked, evidenced
open row per this pass's brief ("leave architectural items… as documented open rows").

### P2 — `realistic` tier orbit/walk drags briefly halve the drawing buffer mid-gesture (desktop
AND phone) — confirmed working as designed, not a regression

Both arms show `dpr` dropping (1→0.5 desktop, 2/3→1.5 phone) and `raf max` spiking to 50–67 ms at
the instant of the drop (§1). This is `InteractiveDprController`'s GPU-STARVE-1 degrade doing
exactly its documented job — the spike is the resize's own long frame
(`GPU-STARVE-3`'s "a resize IS a long frame"), which is the mechanism, not a bug. Recorded here
because it is real, measured, user-visible (a brief blur during a drag on `realistic`), and
because a future change to the degrade threshold should be checked against these exact numbers.
No fix needed or attempted.

### P3 — Program churn on a tier switch is now the single largest recompile event measured, not
the walk-switch or lights-switch documented by z16

§3: tier switch performance→realistic costs **+63 programs** (desktop) / **+90** (phone) against
the walk-switch's +27/+33 and the lights-switch's +3/+4/+28/+1. Already covered by the shipped
`TIER-CHANGE-VEIL` (a readiness-held unbranded veil, not a fixed timer) — flagged for the record
since it re-centres which switch is actually the most expensive one to hide, but no fix needed:
the existing mitigation already targets exactly this event.
